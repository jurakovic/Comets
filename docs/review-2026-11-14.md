# Review of the web app — 14 November 2026

A review of the whole of `app/` on `dev` at `e7403c7` (M4 S1–S8 done; S9 Filters panel, S10 Settings view and the M4 close-out still open). It was asked for outside the plan's close-outs, so it does not replace `review-m4.md`: that review still has the services, the storage and the UI architecture to read against spec 05, 09 and 12.

The reviewer read the code for correctness, reuse and efficiency. Findings 1 and 4 were reproduced in headless Chromium; the others were confirmed by reading the code they name. Nothing was fixed: every outcome is open.

Two findings are visible in normal use: **the Database view stays on screen under every other view**, and **a database that loads late overwrites an import or a deletion made before it**.

| # | Severity | Finding | Outcome |
|---|---|---|---|
| 1 | High | The Database view never hides. `.database-view { display: grid }` (`app/css/database.css:3`) overrides the `hidden` attribute the router sets (`router.js`, `showInOutlet`). After `#/database` → `#/help` the element has `hidden === true` and still computes `display: grid`, 600 px high, with the Help view appended below it. `__body` and `__empty` have `[hidden]` rules; the view itself has none | Open. A `.database-view[hidden]` rule fixes this view; a global `[hidden] { display: none !important }` in the base styles prevents the same mistake in the views to come. An e2e test that the view left is not visible |
| 2 | High | `load()` overwrites what was changed before it finished (`app/js/services/database.js:75`). `main.js` starts the router before `startup.start()`, so the app is usable while IndexedDB is still opening, for up to its 5 s timeout. An import or a deletion in that time sets the list and queues a save; then `set(await repository.load(), 'load')` replaces the list with what storage held and resets the filters. Memory and storage disagree until a reload | Open. The database needs a loaded state: either nothing changes it before the load lands, or a load that lands after a change is dropped. A unit test with a repository whose load resolves after an `apply` |
| 3 | Medium | "The database is empty." shows on every start with a stored database (`app/js/ui/views/database/database-view.js:63`). The empty state is `total === 0`, which is also true before the load has landed, so the view offers **Download comet elements** until it does; a click there leads into finding 2. `Startup.empty` (`services/startup.js:52`) carries the fact and nothing reads it | Open, with finding 2: the view shows the empty state only once the database has loaded |
| 4 | Medium | Close leaves the Update dialog open when the hash changed under it (`app/js/ui/shell/router.js:120`). `returnable` is set only when the overlay opens, so `leaveOverlay()` goes Back once, whatever the number of entries the dialog has made. `#/database` → `#/update` → `#/update?automatic` → Close ends on `#/update` with the dialog open, reset to normal mode. It happens when the user opens Update before the start-up question and then answers Yes | Open. A second hash for the open overlay should replace its entry rather than add one (`main.js` could `location.replace` when the overlay is already shown), or the router counts the entries the overlay made. An e2e test of the sequence above |
| 5 | Medium | Nothing falls back to the local job runner (`app/js/main.js:40`). `worker ??= createWorkerJobRunner(…)` keeps the runner, and one that failed rejects every later job (`adapters/job-runners.js`, as review M3, finding 2, made it) "so the composition root can turn to the local runner". The composition root never does, and `createLocalJobRunner` is used nowhere in `app/`. Latent: no view runs a job before M5 | Open. `main.js` replaces the runner with the local one on the Worker's failure and runs the failed job again. Tested in Chromium with a Worker URL that does not load |
| 6 | Low | The live clock can run ahead (`app/js/core/time/live-clock.js:68`). `tickDelay` returns a few milliseconds when the clock reads just before the boundary + 20 ms, and each tick adds a full second. With a coarse `Date.now()` (Firefox `resistFingerprinting`, Tor Browser: 16.7–100 ms) a tick that ran at X.020 reads X.0167, and the next comes 3.3 ms later; a clock stepped backwards does the same once | Open. A delay under some floor waits for the boundary after the next one. A unit test of `tickDelay` just before the tick point |
| 7 | Low | Every live tick builds the date picker's tooltip (`app/js/ui/components/date-picker.js:53`). `setValue` is `show`, which calls `timeZone()` (`adapters/clock.js`: a new `Intl.DateTimeFormat` each time) and `localText` for a `title` nobody is reading; `pointerenter` (line 78) refreshes it anyway | Open. `setValue` sets the text and the value; the title is built on `pointerenter` and on focus |
| 8 | Low | The Database view's `show()` does the live block's work twice and rebuilds the list (`app/js/ui/views/database/database-view.js:95`). `render()` → `choose()` → `details.show()` → `live.show()` → `resume()` → `computeFirst()`, then `details.start()` → `resume()` → `computeFirst()` again. `list.show()` makes one `<li>` per comet on every show, also on each return from the Update dialog, and the list loses its scroll position | Open. Start before rendering, or skip the second resume; skip `list.show` when the comets are the same array |
| 9 | Low | Repeated code. The presets menu is the same `createMenu` block in `date-editor.js:49–56` and `date-picker.js:62–69`, apart from `run` and a `date-editor__presets-icon` class with no CSS. "Remember the focused element, `showModal`, remove the dialog on close, focus again if still connected" is written out in `shell/dialogs.js`, `components/date-editor.js` and `views/update/import-result-browser.js` | Open. One `presetsMenu(context, onPick)` and one modal helper, before the Filters panel and the Settings view add a fourth |
| 10 | Low | The XEphem reader branches on the orbit kind with a `switch` (`app/js/core/formats/xephem.js:55`), and the writer repeats the three kinds as an `if` chain (lines 104–106), against "registries instead of `switch`es on a kind" (spec 12, `CLAUDE.md`) | Open. A frozen table keyed by `e`, `p` and `h` with each kind's read and write |

## Suggested order

1. Finding 1 first: one CSS rule, and it affects every navigation away from the Database view.
2. Findings 2 and 3 together: they share the missing loaded state.
3. Finding 4 before the Filters panel (M4 S9), while the router is fresh.
4. Findings 5–10 with the M4 close-out (S11); finding 5 must be done before the Ephemeris view runs its first job (M5 S2).
