# Review of the web app — 14 November 2026

A review of the whole of `app/` on `dev` at `e7403c7` (M4 S1–S8 done; S9 Filters panel, S10 Settings view and the M4 close-out still open). It was asked for outside the plan's close-outs, so it does not replace `review-m4.md`: that review still has the services, the storage and the UI architecture to read against spec 05, 09 and 12.

The reviewer read the code for correctness, reuse and efficiency. Findings 1 and 4 were reproduced in headless Chromium; the others were confirmed by reading the code they name. Nothing was fixed: every outcome is open.

Two findings are visible in normal use: **the Database view stays on screen under every other view**, and **a database that loads late overwrites an import or a deletion made before it**.

| # | Severity | Finding | Outcome |
|---|---|---|---|
| 1 | High | The Database view never hides. `.database-view { display: grid }` (`app/css/database.css:3`) overrides the `hidden` attribute the router sets (`router.js`, `showInOutlet`). After `#/database` → `#/help` the element has `hidden === true` and still computes `display: grid`, 600 px high, with the Help view appended below it. `__body` and `__empty` have `[hidden]` rules; the view itself has none | **Fixed.** A global `[hidden] { display: none !important }` in `shell.css`, the base styles, replaces the four per-element rules; it also hid JPL Info, which `a.button` showed with no comet selected. The shell test checks that exactly one view in the outlet is visible after each navigation |
| 2 | High | `load()` overwrites what was changed before it finished (`app/js/services/database.js:75`). `main.js` starts the router before `startup.start()`, so the app is usable while IndexedDB is still opening, for up to its 5 s timeout. An import or a deletion in that time sets the list and queues a save; then `set(await repository.load(), 'load')` replaces the list with what storage held and resets the filters. Memory and storage disagree until a reload | **Fixed.** `DatabaseState.loaded`; Import, Delete and Clear all data wait for the load (and change the state in the call once it has landed, which Delete's index relies on), so they change the stored database; a load that fails leaves it empty and loaded. The Update dialog's counts follow the database while it is open, so a preview made before the load is counted again when it lands. Unit tests with a repository whose load lands late or fails; an e2e test with IndexedDB's open held back: an Import made meanwhile waits, and the reload finds it |

Spec 01 and 05 say so |
| 4 | Medium | Close leaves the Update dialog open when the hash changed under it (`app/js/ui/shell/router.js:120`). `returnable` is set only when the overlay opens, so `leaveOverlay()` goes Back once, whatever the number of entries the dialog has made. `#/database` → `#/update` → `#/update?automatic` → Close ends on `#/update` with the dialog open, reset to normal mode. Latent: no view runs a job before M5 | **Fixed.** `createFallbackJobRunner` (`adapters/job-runners.js`) runs jobs in the Worker until it fails or cannot be made, then on the main thread, the jobs the failure rejected again included; the Worker's runner rejects with a `WorkerFailure`, so a job's own error or its cancel never turns it local. `main.js` loads `core/jobs.js` for it only then. Unit tests of `tickDelay` just before the tick point, and ten ticks under clocks coarsened to 100 ms and 16.7 ms and one 20 ms behind. Spec 05 says so |

Found while fixing finding 4: **the Update dialog left itself after Back and then Forward at once**. `hide()` closes the dialog, and its `close` event comes a task later; when Forward had reopened the dialog by then, the event found it shown and left it. **Fixed**: a `close` event that finds the dialog open is ignored. An e2e test dispatches the stale event; finding 4's test, whose Back and Forward met it about half the time, now answers the start-up question as a user does.

## Suggested order

1. Finding 1 first: one CSS rule, and it affects every navigation away from the Database view.
2. Findings 2 and 3 together: they share the missing loaded state.
3. Finding 4 before the Filters panel (M4 S9), while the router is fresh.
4. Findings 5–10 with the M4 close-out (S11); finding 5 must be done before the Ephemeris view runs its first job (M5 S2).
