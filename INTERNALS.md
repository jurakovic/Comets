# Internals

How the web app in `app/` is built: its layers and what each may depend on, where state lives, how long work runs, how the data is stored, and how it is tested. It describes the code as it is; a change to the code updates it in the same commit.

The desktop app in `src/` is the reference for behaviour: the web app computes, parses and writes data exactly as the desktop does, and the [test vectors](#test-vectors) generated from the desktop sources check that it does. Its own notes are in `docs/`.

## Principles

- **Correct by construction.** Everything the vectors cover lives in pure, DOM-free modules that run unchanged in the browser, in a Worker and under `node --test`.
- **Deterministic.** Nothing in the computing code reads the clock, the time zone, the observer or storage on its own. They are passed in, so a test fixes them.
- **Replaceable parts.** The UI depends on services and on the few ports its context hands it, services depend on ports (interfaces), and adapters implement the ports. Storage, network, workers and the clock can each be swapped or faked.
- **Open for extension.** Element formats, comet properties, compare operators, chart types, simulation steps, routes, commands and jobs are entries in registries. Adding one means adding an entry and its module, not editing a `switch` elsewhere.
- **No build step.** The files under `app/` are what GitHub Pages serves, at `/Comets/app/`. Tooling (lint, types, tests) is development-only and never shipped. There are no runtime dependencies.

## Layers and the dependency rule

Dependencies point inwards: `ui` → `services` → `core`. `adapters` implement the ports: what `services` need, and what views use themselves through their context. `main.js` is the only module that knows every layer.

| Layer | May import | May not use |
|---|---|---|
| `lib/` | `lib/` | anything app-specific; browser or Node globals |
| `core/` | `core/`, `lib/` | browser or Node globals (`window`, `document`, `self`, `localStorage`, `indexedDB`, `fetch`, `navigator`, timers…); `Date.now()`, `new Date()` without arguments, `Math.random()` |
| `services/` | `services/`, `core/`, `lib/` | the DOM, storage, network: those come in through ports. Allowed globals: `AbortController`, `AbortSignal`, `DOMException`, `setTimeout`, `clearTimeout`, `queueMicrotask`, `structuredClone`, `console` |
| `adapters/` | `adapters/`, `core/`, `lib/` | `services/` (they implement its ports by shape, not by import), `ui/` |
| `workers/` | `workers/`, `core/`, `lib/` | the DOM |
| `ui/` | `ui/`, `services/`, `core/`, `lib/` | `adapters/`: the UI gets what it needs from `main.js` through the views' context |
| `main.js` | everything | |

The tooling holds these rules:

- **ESLint** (`eslint.config.js`): the imports per folder (`import-x/no-restricted-paths`), import cycles (`import-x/no-cycle`), the globals per folder, and in `core/` and `lib/` the clock and randomness (`no-restricted-syntax`). In `core/` it also bans what JavaScript does unlike .NET: the `Date` global, `parseFloat`, `parseInt`, `Math.round`, `localeCompare`; in all of `app/js`, `toFixed` and `substr`. A module has at most 400 lines of code.
- **TypeScript** over JSDoc (`checkJs`, `strict`), run three times: `jsconfig.core.json` checks `core/` and `lib/` with the language alone, `jsconfig.worker.json` checks `services/` and `workers/` with Worker types, and `jsconfig.json` checks `ui/`, `adapters/` and `main.js` with the DOM. A stray `document` in a service fails the type check as well as the lint.

`core/` may use `Intl` (time zones, collation): it is part of the language, and its results depend only on its arguments.

## Core

The domain is **plain data and functions**:

- Records (a comet, an ephemeris row, a filter, the settings of a calculation, a graph model) are plain objects, frozen when created. They have no methods and no class identity, so they cross the Worker boundary by structured clone unchanged, compare by value in tests, and serialise as they are.
- Each record has a **factory** in the module that owns its shape, and its JSDoc `@typedef` lives there too. `createComet(fields, fixed)` (`core/comets/comet.js`) derives P, a, Q and n and takes `T` and the sort key apart from the fields, so a comet spread into a new one gets both afresh.
- Validation returns a result instead of throwing (`core/validation.js`): `{ ok: true, value }` or `{ ok: false, errors }`, each error with the `field` it belongs to (and the `index` of its row in a list), so the UI can point at it. It returns every error, in the desktop's order.
- Parsing never throws to its caller. A format's record parser reads its fields with the operations of `core/formats/text.js`, which throw `InvalidRecord` when one fails; `attempt` turns that into a `null` record at the record's edge, and anything else that throws is a bug. The `parse*` functions of `core/format/parse.js` return `null` instead, for callers that are not parsers.
- `throw` is for programmer errors only: an unknown registry key, a broken invariant.
- Time is numbers. An instant is UTC milliseconds since the epoch, a JD is a float64, and calendar arithmetic works on `{ year, month, day, hour, minute, second }` parts. `core/time/calendar.js` converts instants and parts with day-count arithmetic instead of `Date`, so years 0–99 and ≤ 0 need no special case; adding months and years follows .NET's `AddMonths` and `AddYears` (the day clamped, the time of day kept). `now`, the time zone and the observer are parameters.
- Values that depend on the session (`Tn`, `Perih*`, `Current*`) are not fields of the comet. Core functions that need them take a **value accessor** `(comet, key) => number | string` (`core/comets/properties.js`), which the Observations service provides with its cache. So filtering, sorting and quick selection stay pure, and the caching rules live in one place.
- Long computations are generators (see [Long computations and the Worker](#long-computations-and-the-worker)).

| Folder | Holds |
|---|---|
| `core/time/` | `JD0`, `JD` of an instant, `JDToDateTime`, instants ↔ date parts for any year, calendar arithmetic, the date range (1700–2300), local time through `Intl` with an explicit time zone, the Database view's live clock |
| `core/format/` | .NET custom number formats (`number.js`: the exact decimal digits of a float64, rounded to 15 significant digits) and composite format items (`{0,-47:0.000}`, compiled once with `compileFormat`), date patterns and saved files' names, `HMS` and `Angle`, how long ago a date was; numbers and white space read as .NET reads them (`parse.js`) |
| `core/comets/` | the comet record and its derived elements, designations and sort keys, the property registry and compare operators, filters, sorting (`compareText` in `collation.js`), quick selection, merging an import, the counts the shell shows, the Database view's detail rows and live values |
| `core/astro/` | constants and degree helpers, the Kepler solvers, comet and Sun positions, the ephemeris record, precession, planets, orbit sampling |
| `core/formats/` | text conventions and field access, the record parsers' shared end (`record.js`), the format registry, detection, import and export, one module per format |
| `core/ephemeris/` | ephemeris settings (defaults, validation, the long-calculation count, the title), the timespan and its steps, the output columns, the calculation, the text output |
| `core/graph/` | graph settings and chart types, sampling, the **graph model** (axes, series, perihelion and now lines, title) a renderer draws and the vectors check, hover hit-testing |
| `core/orbit/` | the orbit viewer's simulation steps: the step menu and the single steps |
| `core/input/` | the rules of the shared input components: what a number field accepts and how `↑`/`↓` step it; the date picker's fields, texts, JD field, clamp and presets; the location's latitude and longitude fields; the filters panel's rows, each edit of them and the filters they give |

### Matching the desktop

The core reproduces the desktop's results, its quirks included. Where the web app deliberately differs from the desktop (it fails where the desktop throws or hangs, it spells a label right, it encodes a URL), the comment at that code says so; so does one where a surprising result is the desktop's on purpose. Desktop names in comments and JSDoc (`CometManager`, `ExportMpc00`, `FormUpdate`) say which desktop source a rule comes from.

JavaScript differs from .NET in ways that pass casual tests; `CLAUDE.md` lists them under "JavaScript against .NET", and lint bans the worst in `core/`.

## Services and ports

A service is a use case together with the state it owns. Each is created by a factory that takes its dependencies (constructor injection):

```js
const database = createDatabaseService({ repository, clock, settings });
```

| Service | Owns | Does |
|---|---|---|
| `settings` | the settings | loads, validates, migrates and saves them; owns the rule of each value |
| `database` | the main collection (`DatabaseState`: the comets, the change that made them, whether the load has landed) | loads it at start-up, previews and applies an import, deletes, clears; saves after every change, and gives the stored text for Export database. Changes wait for the load, so a load that lands late cannot replace them |
| `database-repository` | | the stored form of the database: MPC text, written whole and read back as an MPC import |
| `selection` | the app-wide filters, sort and selection | follows the database: a deletion takes the comet out and sorts again; anything else starts from the default filter rows with the current sort. A sort re-sorts the selection as it is, so ties keep the previous order |
| `observations` | the session cache of `Tn`, `Perih*`, `Current*`, per comet record | provides the value accessor; `Current*` are recomputed after 5 minutes |
| `update` | the Update dialog's state: the download (`idle`, `running` with progress, `done`, `failed`), the file, the candidate source, the preview | downloads with progress and cancellation, reads files, previews against the database as it is, imports; `closesAfterImport` decides whether the dialog closes |
| `jobs` | the running long computations | runs them through the `JobRunner` port; exposes their progress and cancellation to the status area |
| `startup` | | loads the settings and the database; `updatePrompt(settings, now)` is the start-up question, which the shell asks |

**Ports** are the services' view of the outside world, named in `services/ports.js` as JSDoc typedefs. A view that needs one itself (the clock, the geolocator) gets it through its context, never the adapter:

| Port | Shape | Adapters |
|---|---|---|
| `Clock` | `now(): number`, `timeZone(): string` | the system clock (`adapters/clock.js`); a fake clock in tests |
| `KeyValueStore` | async `get`, `put`, `remove` of strings | IndexedDB, Web Storage, memory (`adapters/key-value-stores.js`); see [Storage](#storage) |
| `TextFetcher` | `fetchText(url, { signal, onProgress })` | `fetch` with a stream reader, decoded by the byte-order mark (`adapters/text-fetcher.js`) |
| `TextFileReader` | `readText(file)` | a `Blob` read whole, decoded by the byte-order mark (`adapters/text-files.js`) |
| `JobRunner` | `run(name, input, { signal, onProgress })` | a module Worker, the same protocol on the main thread, and the fallback between them (`adapters/job-runners.js`) |
| `Geolocator` | `locate()`: the device's latitude and longitude, once the user allows it | the Geolocation API (`adapters/geolocation.js`) |

Bytes become text in `adapters/text-decoding.js`, as `File.ReadAllLines` reads them: UTF-8, or UTF-16 or UTF-32 by a byte-order mark, which is dropped; invalid bytes become U+FFFD. `TextDecoder` is not in core.

Services never talk to the user. When something needs asking (the start-up update question, a long-calculation warning, a delete confirmation), the service or a core function returns what to ask, and the view asks and calls back. Services never import the UI.

## State and change

- **One owner per piece of state.** Each piece belongs to one service (or, for view-local state such as a form's fields, one view) and is changed only through that owner's functions.
- **Observable stores** (`lib/store.js`): `get()`, `set()`, `update()` and `subscribe(listener)`, which returns the unsubscribe function; listeners hear of a change only when the value differs (`Object.is`). An owner hands out `readonly(store)`. Views subscribe when shown and unsubscribe when hidden. There is no global store.
- Records are immutable; a change produces a new record or a new list, so a store compares by reference. A store notifies synchronously, so whoever needs the state from before a change records it first.
- Things that happen rather than state that is go through a function: `notify(message, { kind })` for a notification, a callback given to a component.

## Storage

Browser storage is per origin. Everything the app stores:

| Data | Store | Key | Format |
|---|---|---|---|
| Settings | `localStorage` | `comets.settings` (`SETTINGS_KEY`) | JSON with a `version` and the settings' values; `lastUpdateDate` as an ISO 8601 UTC text |
| Database | IndexedDB `comets`, object store `kv` | `database` (`DATABASE_KEY`) | the MPC text of the main collection |

- Every store is wrapped by `tolerant` (`adapters/key-value-stores.js`): a write or removal the storage refuses (missing, full, blocked, broken) is kept in memory and wins over the storage until a later write of the same key gets through; a read that fails gives `undefined`. An IndexedDB that throws, errors, is blocked or has not opened after 5 s fails the session's later calls at once. Storage never stops the app.
- Writes go through a queue (`lib/queue.js`), one after another in the order they were made, so the last change is the one that stays. The database is written in one `put` of the whole text after every change, and removed by Clear all data, which removes the settings too.
- Settings are read value by value (`readSettings`): a value that is missing or outside its rule takes its default, and the others are kept; text that is not settings JSON gives the defaults. Older versions run through `MIGRATIONS` first (`SETTINGS_VERSION` is its length + 1); a newer version's values are read where they follow this version's rules. A value outside its rules in an update is a programmer's error: the inputs keep to the rules.

## Long computations and the Worker

Ephemerides and graphs over many comets run off the main thread.

- A long computation is a **generator** in `core/` that yields progress (`{ done, total }`, in comets) and returns its result. It runs as fast as it can when iterated synchronously (Node tests), and gives a runner a point to report progress and check cancellation between steps. The calculations yield per comet and every 2000 rows.
- `core/jobs.js` maps job names to those generators: `ephemeris` returns the ephemeris text, `graph` the graph model. Inputs and results are plain data. Values cached for the session (`Tn`, the observer, `now`) go into a job's input on the main thread, so a result never depends on which thread computed it.
- `lib/rpc.js` is the message protocol: `run` → `progress`* → `result` | `error`, and `cancel`. The server runs a generator in time slices, posting the latest progress after each, and schedules the next slice as a task, so that a `cancel` is read between slices (a slice already queued still runs).
- The Worker (`workers/compute.js`) serves `JOBS` with 50 ms slices, scheduling each slice as a message to itself through a `MessageChannel`. The local runner joins the same server and client on the main thread with 20 ms slices and clones every message as a Worker would.
- `createFallbackJobRunner` runs jobs in the Worker, which starts with the first job. A Worker that cannot be made or fails (in practice, one that does not load) rejects its jobs with a `WorkerFailure`; from then on the local runner, whose code `main.js` imports only then, runs them, the rejected jobs included. A job's own error or its cancel does not switch runners.

## UI

### The shell

`index.html` holds the landmarks; `main.js` builds the adapters, the services and the shell, starts the router, then runs start-up, and asks its question once the route the page opened on is shown, so that a dialog route's `<dialog>` cannot open over it.

- **Routes.** `ui/shell/routes.js` is the route table: each route's key (`#/<key>`), title, group (the views, or the app's own pages) and `load(context)`, which creates the view with `import()` on its first visit. The router (`ui/shell/router.js`) shows the route the hash names, with its parameters (`#/update?automatic`); an unknown or empty hash opens `database`. A view is kept after its first visit, which keeps its state for the session, and hidden with the `hidden` attribute when another takes its place.
- **Views** implement `{ element, show(params), hide(), save?() }`. `hide()` stops their clocks; `save()` is what `Ctrl/⌘+S` runs.
- **Dialog routes.** A route marked `overlay` (Update) is a `<dialog>` over the view shown, which stays under it. The router counts the history entries the dialog route has made since a navigation opened it, keeps the count in each entry's history state, so that Back and Forward find it again, and `leaveOverlay` goes back past them all; a dialog route reached otherwise replaces the hash when it closes. Esc closes the dialog natively and the route follows.
- **Context.** Each view gets an `AppContext` (`ui/shell/context.js`): the clock, the geolocator, the services, the command registry, the dialogs, `notify` and `leaveOverlay`.
- **Commands** (`ui/shell/shortcuts.js`): every action a key runs is a command registered by id with its label, key bindings (exact modifiers; `mod` is Ctrl or ⌘), whether it runs in text fields, and an `enabled` test. One keydown dispatcher and the Help's list of controls are written against the registry. `main.js` registers `save` and `close-dialog`.
- **Dialogs** (`ui/shell/dialogs.js`): confirmation questions as modal `<dialog>`s on a stack, answered by a button; the Esc command closes the top one as No. `ui/components/modal.js` (`openModal`) is the modal life cycle the question, the date editor and the import result browser share: added to the page, removed when it closes, and the focus given back.
- **Notifications** (`ui/shell/notifications.js`): a live region that is a manual popover, shown again for each notice so that it paints above a modal dialog. Information goes after 5 s, an error stays until dismissed, at most four at once.
- **Errors** (`ui/shell/errors.js`): `error` and `unhandledrejection` are logged and shown as a notification, so one failing part does not leave the page silently broken; a cancellation is not shown.
- **Navigation and status.** `nav.js` builds the navigation from the route table, marking the route shown, with how long ago the last update was under Update. `status.js` shows the comet count, which opens the Database view, and the latest running job's progress with Cancel.
- **Theme** (`theme.js`): `html[data-theme]` holds an explicit light or dark choice; without it the OS decides through `prefers-color-scheme`. It follows the setting live.

|---|---|
| `database` | `views/database/`: the selection as a listbox (`comet-list.js`), its sort menu, the filters panel, Reset and Delete, the selected comet's details (`comet-details.js`: the Ephemeris tab with its live block, `live-ephemeris.js`, and the Orbital elements tab with JPL Info), and the empty state once the database has loaded empty. ### How the UI is written

- **Humble views.** A view turns state into DOM and DOM events into service calls; it decides nothing. What to show (texts, numbers, colours, which rows) comes from pure functions in `core/` or a service, which the unit tests and vectors check. The Database view's rows are `core/comets/details.js`; the live clock's rules are `core/time/live-clock.js`; the input components' rules are `core/input/`.
- **Components** are ES modules that create and own a DOM subtree, expose `element` and a small API, and report changes through callbacks given to them. They do not read services: their owner passes data in. No framework, no virtual DOM, no custom elements.
- **The filters panel** (`ui/components/filters-panel.js`) edits up to ten filter rows, each with a checkbox, the property and compare as `<select>`s, the property's editor (a text field, a number field or a date picker, each keeping its own value) and unit, and a remove button. Its owner gives it an `apply` that returns the validation, and the panel shows an error by its row; Apply and Enter (the panel is a `<form>`) apply too, and focus the field in error.
- **Menus** (`ui/components/menu.js`) are popovers whose entries are built as they open, with the arrow keys, Home, End and their own Esc, and the focus back on the button; they stay hidden until placed, and open on the roomier side. The sort menu and the date presets are menus.
- **Styling.** Theme colours and sizes are custom properties in `css/tokens.css`, redefined for the dark theme. `css/shell.css` holds the base styles, among them a global `[hidden] { display: none !important }`, so a component's own `display` never shows a hidden element. Each area has its own stylesheet; class names are prefixed by their component or view (`database-view__body`).
- **Accessibility.** Controls are native elements wherever one fits; dialogs, menus, tabs and the comet listbox carry their ARIA roles and manage focus; everything works from the keyboard.

## Errors

- Expected failures are values: validation results, `null` records, a download error the `update` service turns into its message.
- Storage failures fall back to memory and never stop the app ([Storage](#storage)).
- A Worker that fails falls back to the main thread ([Long computations and the Worker](#long-computations-and-the-worker)).
- Cancellation uses `AbortSignal` everywhere and is not an error to show.
- What nothing else catches reaches the shell's error handler ([The shell](#the-shell)).

## Testing

| Level | Runs | Checks |
|---|---|---|
| Unit | `node --test tests/unit` | `lib/`, `core/`, `services/` with fakes from `tests/helpers/fakes.js`, the adapters with fake storage and fetch, the router's and shortcuts' pure parts |
| Vectors | `node --test tests/vectors` | every file of `tests/vectors/data` within its [tolerances](#tolerances); the ephemeris and graph jobs also through the `rpc` protocol |
| End to end | Playwright: `npm run test:e2e` | the app in Chromium on a desktop and a Pixel 7, offline |
| Screenshots | Playwright: `npm run screenshots` | every view in both themes at desktop and phone size, written to `test-results/screenshots/` |

`npm run check` runs lint, the three type checks, the unit and vector tests and the browser tests.

- **Browser tests** run against `tests/serve.js`, which serves the repository under `/Comets/` as Pages does, so a wrong absolute path fails. Pages are at `timezoneId: 'UTC'`, `locale: 'en-GB'`. `tests/e2e/fixtures.js` answers every request that leaves the local server with a 404 unless a test answers it (the MPC download is answered from a vector file), and fails a test on any page or console error it does not expect. `seed(page, …)` stores settings and a database where the app keeps them and reloads. Playwright's clock fixes and drives time; a test that needs a history entry made by a gesture answers the start-up question rather than setting the hash, since Chrome's Back and Forward may skip entries made without one.
- **Helpers.** `tests/helpers/vectors.js` reads the vectors (`readVector`, `readVectorText`, `toLf`) and compares within tolerances (`assertClose`, `assertRelativeClose`, `assertAngleClose`); `formats.js`, `ephemeris.js` and `graph.js` turn the vector cases into the app's shapes; `generators.js` drains a generator; `fakes.js` has the fake clock and storage.

## Test vectors

`tests/vectors/data/` holds expected results generated by running the **desktop sources**, linked unchanged, through `tools/spec-vectors`. The web app conforms when it reproduces them within the tolerances below. They are never edited by hand.

### Frame of reference

| | |
|---|---|
| Clock | Frozen at **2026-10-18 12:00:00 UTC** (`JD 2461332.0`, `VECTOR_NOW` in the helpers). Every "now", "today", `Tn` and `Current*` value refers to it. |
| Time zone | UTC, except the local-time ephemeris cases, which are `Europe/Zagreb` |

| `ephemeris-text/NN-*.txt`, `index.json` | The full ephemeris text for 5 settings cases: UT and all columns; several comets with a requirement; 2 h 30 min steps with a subset of columns; local time across a DST change; a parabolic comet |
| `graph.json` | The sampling-interval table and 5 graph cases: axis ranges, ticks, label formats, and every series with its points (x as JD) |
| `simulation-steps.json` | Calendar single steps forward and back |
| `planets.json` | Planet elements, perturbations and positions at 8 dates |
| `orbit-viewer-positions.json` | Comet positions (ecliptic of date) at 4 dates |
| `orbit-sampling.json` | Orbit-line samples in the orbital plane for 7 comets (count and indexed points) |
| `engine-comparison.json` | The web app's engine against the desktop orbit viewer's own. **Not a test** |

The sample collection includes on purpose:

- numbered periodic comets, defunct (`D`) comets, fragments (`73P-BT`, `96P-B`, `141P-A`, `3D-A`, `C/1947 X1-B`, `C/2023 R1-B`) and interstellar objects (`1I`, `2I`, `3I`);
- `A/` objects, an old-style designation (`C/1942 EA`), and q ≥ 10 AU (`C/2014 UN271`, `C/2019 E3`);
- P > 30000 years (`C/1999 F1`), near-parabolic hyperbolas (`C/2013 A1`) and a short day fraction (`18D`);
- five **synthetic** comets: an exact parabola `C/2026 T99 (Parabola Test)`, a negative year `C/-146 P1`, an `X/` type `X/1106 C1`, and digit fragments `D/1993 F2-A`, `C/1860 D1-A`.

### Tolerances

| Quantity | Tolerance |
|---|---|
| JD values (`time.json`, `T`, `Tn`) | 1·10⁻⁸ day |
| Instants (dates from a JD, `Tn` dates, simulation steps) | Exact |
| Parsed element values | Exact (float64 parsing of the same text). Computed ones (xephem `q`, MyStars `w`, NASA angles): 1·10⁻⁹ |
| Derived P, a, Q, n | Relative 1·10⁻¹² |
| Angles (RA, Dec, Alt, Az, ecliptic longitude and latitude, elongation, position angle) | 1·10⁻⁶ °, compared modulo 360 |
| Distances (Sun and Earth distances, planet and comet coordinates) | 1·10⁻⁸ AU |
| Magnitudes | 1·10⁻⁸ |
| Orbit-sampling points | Exact count; coordinates 1·10⁻⁹ AU |
| Graph x values | 1/86400 day (the desktop chart stores whole seconds) |
| Texts: names, sort keys, export and ephemeris text, detection results, lists of full names | Exact |

Lists produced by sorting or filtering match exactly, in order.

### Regenerating

`tools/spec-vectors/run.sh` builds the generator and runs it with the clock frozen by libfaketime and `TZ=UTC`; it needs the .NET 8 SDK and libfaketime (`tools/spec-vectors/README.md`). A plain run reproduces the committed vectors byte for byte, which CI's Spec vectors workflow checks. A run on fresh downloads rebases the vectors on new MPC data; the inputs and outputs are then committed together.

## CI

`.github/workflows/`:

- **Web** (`web.yml`) runs `npm run check` and the screenshots on `dev`, `master` and pull requests, when the app, the tests, the vectors or the tooling change, and on demand. The screenshots are uploaded as the `comets-screenshots` artifact.
- **Spec vectors** (`spec-vectors.yml`) regenerates the vectors with .NET 8 and libfaketime and fails on any difference, when the generator, the vectors or the desktop engine (`src/Comets.Core`, `src/Comets.OrbitViewer`) change, and on demand.
